### Should-fix
- `scripts/smoke-po-number-concurrency.sh:92-98,110-125` — The "B finished while A was still open" check is timing-dependent and can fail on a slow machine. A sleeps a fixed 3 s. B's `docker exec` start-up (plus the readiness poll) can eat most of that on a loaded Docker Desktop. If A closes first, the script reports "B may have waited on A" even though nothing is wrong. Either lengthen A's sleep (for example 8 s, since only the failure path pays the cost) or check B's duration directly (time B, and require it to be much shorter than A's sleep).
- `scripts/smoke-po-number-concurrency.sh:100-105` — When A never reaches `pg_sleep` the script prints FAIL but carries on, so it starts B anyway, and the later "B never waited on A" checks mean nothing. Abort at that point. Print A's output and `exit 1`, since the rest of the script depends on A being open.
- `scripts/smoke-po-number-concurrency.sh` (placement) / `package.json:18` / `tests/README.md:35-36,393-429` — The smoke is a Track 3 script, but it is not in `test:smoke` and not listed in the README's Track 3 section. It also uses `docker exec psql` where the README describes Track 3 as "bash + curl". Leaving it out of `test:smoke` is reasonable: it needs the local Postgres container, and it is "run by hand" per its header. But it is then invisible to anyone reading the README. Add a one-line README entry saying it is manual-only, why, and that it leaves the local sequence higher. That avoids it being mistaken for an orphaned `*.sh`.

### Nits
- `supabase/migrations/20261109140000_po_number_sequence.sql:43-45` — The header lists `greatest` among functions that "can't be shadowed from public". `greatest` is a SQL conditional expression, not a function lookup, so it cannot be shadowed either way. Drop it from the list so the argument stays exact. `lpad`, `length` and `nextval` are correct.
- `supabase/migrations/20261109140000_po_number_sequence.sql:139` — `set search_path = public` on the formatter blocks SQL-function inlining, and the body only uses `pg_catalog` objects, so the pin buys nothing. The design chose it deliberately and DP-5 asserts it, so this is not a change request. A comment saying "pinned for uniformity with the trigger function, not needed for safety" would help the next reader decide whether to remove it.
- `supabase/migrations/20261109140000_po_number_sequence.sql:158,163-164` — `v_n` is used once. `v_candidate := public.format_po_number(nextval('public.purchase_orders_po_number_seq'));` would drop a variable. Keeping it is fine for readability.
- `supabase/tests/generate_po_number_sequence.test.sql:268-273,301-306,444-448` — The anti-vacuity probes use one `ok()` that combines three or four conditions. A failure then shows only "not ok" with no hint which fact broke (member can see X, cannot see Y, cannot see Y's PO). Split into separate assertions or use a single `is()` on a text value that spells out the three booleans. This only matters when a regression happens.
- `supabase/tests/generate_po_number_malformed_guard.test.sql:68-81` — The header says the unfiltered delete is kept "to show the counter does NOT reset". The first assertion compares against `seq_next()`. On a fresh sequence (a standalone run on a clean DB) `seq_next()` is 1, so the expected value is `PO-001`. That is also what the old `max()` body would produce, so the assertion cannot tell the two apart. The sequence file's AC-5 does cover "deleting does not reuse", so there is no coverage gap, only an overstated comment. Soften the comment, or note that the assertion is only discriminating once the sequence has moved. (Coverage questions belong to test-engineer.)
- `supabase/tests/generate_po_number_malformed_guard.test.sql:86-90,120-124,136-140` — The "previous generated + 1" assertions break if any other session inserts a PO between two of this file's inserts. That is possible on the shared local DB, because a nextval outside this transaction cannot be rolled back or hidden. CI is serial, so it can't happen there, and AC-13 asked for this shape. Say so in the header, so a local flake is not read as a regression.
- `supabase/tests/generate_po_number_sequence.test.sql:56-93` and `generate_po_number_malformed_guard.test.sql:55-66` — `seq_next()` and `num()` are defined in both files. Test-local helpers are the norm in this folder, so I'd leave them. If a third file needs them, move them to a shared helper.
- (out-of-scope) `supabase/tests/retention_prune_job.test.sql:259-262` — Stale workaround comment, correctly left untouched while spec 186 is uncommitted (D-6). It is already in the spec's "Noticed, not changed" list. Clean it up when 186 lands.
- (out-of-scope) `specs/186-retention-purge-server-job.md` cites `generate_po_number_malformed_guard.test.sql:38` (lines 182, 355, 727). The unfiltered delete is now at line 70. Already recorded in the spec.
