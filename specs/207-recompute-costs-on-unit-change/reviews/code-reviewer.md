For the seven modified files I could only inspect the spec-207 comment hunks and T72/T73 (no `git diff` available in this session), so fixture value changes were checked against their comments, not line by line. Test files follow the established pgTAP and jest tracks.

### Critical

### Should-fix
- `supabase/tests/apply_item_scalars_to_brand.test.sql:236-243` — Assertion (15), "NULL-means-skip: cost_per_unit LEFT ALONE", can no longer fail for the thing it names. Charles's row is now priced (case 240, pieces 12), so R3 re-derives 20.00 whatever `apply_item_scalars_to_brand` does with a NULL `p_cost_per_unit`. A regression that overwrote cost with NULL or 0 would still pass, because R3 would put 20.00 back. The comment admits this, but the assertion title still claims it pins the no-op. The spec's own rule is "update, don't weaken". Add an unpriced row (case_price 0, hand-picked cost) to the NULL-skip call and assert its cost survives, keeping (15) as the derived-value pin. Retitle (15) so it no longer implies the NULL-skip semantic.
- `supabase/migrations/20261123130000_recompute_costs_on_pack_size_change.sql:493-496` — The copied comment above the catalog select says both values "coalesce to >= 1, so the divisor ... is >= 1 and never zero". That is false for `case_qty = 0`: `coalesce(0, 1)` stays 0. This migration's own `per_each_cost` call is what now guards it, and the header (L83-86) and AC-9 test advertise the divide-by-zero fix. The implementation notes say it was left byte-identical on purpose. But the hunk is already being re-created, and a comment that now contradicts the code is a maintenance trap. Either fix the comment in the same hunk (and list it in the header's "ONE changed line" statement as a comment-only change), or keep it and add a one-line "NOTE (spec 207)" beside it. I'd prefer the fix.

### Nits
- `supabase/migrations/20261123130000_recompute_costs_on_pack_size_change.sql:240-270` — The same `case when price > 0 then per_each_cost(...) else round(cost * v_old / v_new, 6) end` appears four times (SET and `is distinct from` in each UPDATE). They must stay identical for the "only write changed rows" filter to be correct. A future edit to one copy will silently produce writes of unchanged rows, or skipped rows. Consider a `with` / `cross join lateral (select ... as new_cost)` per UPDATE, as `list_cost_drift` already does for `dc.d`. The spec's design shape used the repeated form, so this is optional.
- `supabase/tests/cost_rederive_on_pack_size.test.sql:375-379` — The AC-11 boolean mixes `and` / `or` without parentheses. It works only because the non-matching table's subselect returns NULL and the `h.tbl` check cancels it. It reads as a bug. Parenthesise each `(... and h.tbl = ...)` arm, or compare per table with a `case h.tbl`.
- `supabase/tests/cost_rederive_on_pack_size.test.sql:25-33` — The catalog index legend omits C20 (the brand-2 catalog row inserted near L740), and AC-6 / R1-scope fixtures (C1 reused for the second change) are not mentioned. Add C20 to the legend so the file's own map matches its fixtures.
- `src/utils/perEachCost.spec207.test.ts:48-52` — The "per_each_cost" leg computes `round6(30 / piecesPerCase(q, s))` in the test and compares it to a literal. That re-implements the SQL formula in TS, so it mostly re-checks `piecesPerCase` (already covered above). Its value is as a pinned-literal table that the pgTAP `_m` table mirrors, which is fine, but the describe title overstates it as parity with `per_each_cost`. Consider renaming it to say the literals are the shared fixture.
- `src/utils/perEachCost.spec207.test.ts:16-18` — NaN standing in for SQL NULL is documented, so no change needed. One extra line saying "`undefined` / `null` would give the same result" would help whoever extends the matrix.
- `supabase/migrations/20261123130000_recompute_costs_on_pack_size_change.sql:90-97` — The PROD APPLY header references "spec 207 D-11" and "D-11 step 1/3". Migrations outlive spec files being moved around, so keep the one-line runbook inline (the header already does most of this) rather than relying on the spec section existing.
