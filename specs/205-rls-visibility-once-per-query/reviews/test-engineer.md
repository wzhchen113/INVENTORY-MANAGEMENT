### Judgement calls requested
1. Would the equivalence suite catch a non-equivalent rewrite (mutation-style)? Yes, largely. The new side is read from the live `pg_policies` (not a pasted copy), so any wrong rewrite of any of the 36 policies is evaluated; the old side is the recorded text run through the still-present old functions. The discriminating fixture set is good: rows at A1/A2/B1, NULL-scope rows, NULL-FK child rows, a soft-deleted brand, and principals that isolate each arm (SA, ADM-A+L with a planted cross-brand link for arm iii, STALE/STALE+L, ROLE-ONLY for the JWT-vs-profile parity trap, STAFF/LOOSE for the brand arm for non-admins). Developer's mutation proofs: dropping the user_stores arm fails 10 assertions; dropping the super_admin arm from one policy fails 4. Plus the AC-6 md5 manifest independently fails on ANY text change to any policy on the 35 tables, so a silent edit cannot pass even if row sets coincide. Residual gaps (low): (i) the write-side `ALTER POLICY` probes cover only the two ALL policies, which is all R4 has; (ii) a rewrite that is equivalent for fixtures but not generally (e.g. a wrong column on a table where both columns are equal in fixtures) is only caught if fixtures differ on that column; fixtures use distinct A1/A2/B1 ids so this is unlikely; (iii) the NOT-context `coalesce(..., false)` in invitations is exercised only via the fixture shapes, since the stated unreachable-today case cannot be produced through real principals.
2. Is anon coverage enough? Yes for the contract: all 35 tables, fixtures present in every table (so 0 rows is meaningful, not "empty table"), errors captured per table (would surface 42501), grants asserted, and ANON is also in the AC-2 old-vs-new comparison. Only gap: anon is simulated with claims `{"role":"anon"}`; a request with no claims at all (empty `request.jwt.claims`) is not separately probed. `auth.uid()` is null in both, so risk is negligible.
3. Will CI's pgTAP job run the new files? Yes: `.github/workflows/test.yml` runs `npm run test:db`, and `scripts/test-db.sh` walks every `.test.sql` under `supabase/tests/`; both new files ran in my full run. Conditions: the two new test files and the migration are currently UNTRACKED (git status `??`); they must be staged and committed together with the four edited pins, or CI/db-migrations gate will not see them. CI pins Supabase CLI 2.106.0 while the local stack here is CLI 2.95.4 / PG 17.6; the S-3 / T3 pins depend on exact `pg_policies` deparse, which is Postgres-version-driven rather than CLI-driven, so this is low risk but is the one thing only the first CI run proves.
