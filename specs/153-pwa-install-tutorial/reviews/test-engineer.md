### Notes

**On the extra shell test (`ResponsiveCmdShell.spec153.test.tsx`) vs §7's "read the branches" substitute.** The design's §7 offered whole-shell AC-2 coverage across all three breakpoints as *optional* — "expensive... acceptable substitute: assert the sheet + entry in isolation and verify the three breakpoints by reading the three return branches at review time." The implementing agent went further and wrote the whole-shell test anyway (flagged explicitly as deviation 1 in the spec's "Implementation notes" section). Ruling: this is the right call, not scope creep. It converts a review-time manual claim into a build-time regression guard for exactly the kind of thing that's easy to silently drop in a future edit (one of three `return` branches, or the rail twin `showInstallEntry` gate, or the nested-Modal drawer-close-before-sheet-open ordering that the design calls out as a Critical-severity risk in §8.3). The test correctly stubs the shell's children to pass-through renderers of the footer *slots* under test while running the shell's own state/gates for real, and it is purely additive — no existing suite was touched to make room for it. I rule this satisfies (and exceeds) AC-2's coverage bar; the "read the branches at review time" fallback is no longer needed and code-reviewer/architect should treat the manual-branch-read as superseded by this test file, not as still-required due diligence.

**ACs dependent on live UA / `beforeinstallprompt` — automated-only so far, manual evidence pending.** AC-9 (the one-tap install button actually firing on real Chrome/Android) and the UA-detection portions of AC-1/AC-2/AC-4 (real iPhone Safari, real Android Chrome, desktop Chrome at 1440×900 and 390×844, plus the es/zh-CN footer-width eyeball the design flags in §8.5) are covered here only by jest suites that stub `navigator.userAgent`, `Platform.OS`, `matchMedia`, and a synthetic `beforeinstallprompt`/`appinstalled` event pair. The spec's own §"Verification" section requires a **manual browser check (not CI)** on real devices, and the implementing agent's notes explicitly state this manual pass was **not performed** ("the implementing agent had no browser preview tooling available"). Per the dispatching prompt, a browser pass is being run in parallel by the dispatcher — treat that as the source of the missing manual evidence; this report does not duplicate it. Until that pass lands, AC-9's live-Chrome behavior and the real-device UA detection are automated-verified-only, not device-verified. I am not marking AC-9 as NOT TESTED because the state machine and every render gate the spec actually asks jest to cover (§7) are pinned and green; the residual risk is the browser-policy opportunism the design itself calls out in §8.1 ("the button may never appear for a given user even with Q3 taken... the manual steps are the contract; the button is a bonus").

**Deviations from the design, both narrow and pre-flagged by the implementer, checked and accepted:**
1. `_resetInstallPrompt()` also tears down installed window listeners (design said event + subscribers only). Test-only, strictly wider, keeps the node suite hermetic — no behavior-under-test is weakened.
2. `promptInstall()` maps a throwing `prompt()` to `'dismissed'` rather than leaving it unstated. Verified by `installGuide.test.ts::a throwing prompt() never escapes as a rejection` — reasonable (a rejected/failed prompt is a non-install, not a crash) and consistent with AC-9's "never throws" framing.

**AC-8's staff-card off-web case.** `InstallGuideSheet.test.tsx` has an explicit `Platform.OS: 'ios'` → renders-nothing test for the admin sheet, and `ResponsiveCmdShell.spec153.test.tsx` has the shell-level equivalent. `Settings.test.tsx` does not add a parallel explicit off-web case for `InstallGuideCard` — it mocks `Platform.OS: 'web'` for the whole suite (matching the existing suite's web-only posture) and relies on `InstallGuideCard`'s own `Platform.OS !== 'web' → return null` guard, which is structurally identical to the sheet's already-tested guard and reads cleanly on inspection. This is a minor coverage gap, not a blocking one — the guard is a one-line early return with no state dependency, the same pattern already pinned twice elsewhere in this diff, and CLAUDE.md's testing-behavior-not-implementation principle argues against demanding a third copy of an identical assertion. Noting it rather than blocking on it.

No pgTAP or shell-smoke additions — correctly, since this spec has zero DB/HTTP surface. `useSyncExternalStore` is a new *React* pattern for this codebase (first use, per the design's own note) but is not a new *test* framework — it is exercised indirectly through the component tests (`InstallGuideSheet.test.tsx`, `Settings.test.tsx`) and directly through the module functions it wraps (`installGuide.test.ts`), consistent with the `sessionWatch.ts` precedent.
