### Notes

- **AC-4's admin/staff call sites are wired but not independently pinned.** The `markIntentionalSignOut()` call in `useStore.ts::logout()` and in `Settings.tsx`'s sign-out handler are both confirmed present by diff inspection, but no test exercises `logout()` or `Settings`'s sign-out handler end-to-end and asserts the toast stays silent — the only pin is `sessionWatch.test.ts`'s direct-flag-then-`handleSessionLoss()` unit test, which validates the *mechanism* (the flag suppresses the toast) but not that the two call sites *actually raise the flag at the right time relative to `signOut()`*. This is a small, real gap: a future refactor that reorders `markIntentionalSignOut()` after `signOut()` in either call site (instead of before, which matters because the event can fire synchronously inside `signOut()`) would not be caught by any current jest suite. Not blocking — the spec's own manual browser recipe explicitly covers this ("AC-4 live check: sign in, press sign out, accept the confirm → sign-in screen with NO 'Session expired' toast") and the code comments in both call sites explain the ordering constraint precisely. Flagging as a coverage gap for a future spec's backlog, not a blocker for this one.
- **Manual Playwright repro not wired into CI, as intentionally documented.** The spec's "Manual browser recipe" section explicitly marks this as ad-hoc and NOT added to `e2e/` or any CI gate, because it's the only way to exercise "the JWT stops being accepted mid-session" (refresh returning 400 `invalid_grant`) — jest/jsdom cannot simulate supabase-js's real token-refresh state machine. I did not re-run this script myself (it requires a live local stack + a super_admin fixture with no `user_stores` rows + manual credential substitution into the driver file), but its presence in the spec as the browser-level evidence for AC-1/AC-8/AC-9's real-world trigger (as opposed to the jest pins' synthetic trigger) is consistent with the project's documented policy that this repro class is deliberately kept out of CI. Treating the spec's "Observed, same driver, both sides of the change" before/after description as the browser-level evidence per the task's framing, not as something I independently reproduced this session.
- **No fourth test framework introduced.** All new tests are jest (`*.test.ts` / `*.test.tsx`), consistent with the existing `jest` track. No vitest/playwright test files were added under `e2e/` or elsewhere.
- **`app.json` slug untouched.** Not relevant to this spec's diff; confirmed no changes to that file.
- **Typecheck gates both clean**, including `tsconfig.test.json` (`typecheck:test`), which is the CI gate that jest itself doesn't catch (per project memory on the phone-tier rollout).
