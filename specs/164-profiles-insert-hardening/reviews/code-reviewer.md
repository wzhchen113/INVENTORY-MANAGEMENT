### Should-fix
- `src/lib/auth.ts:357`, `:379`, `:441-443`, `:450` — Stale comments in `inviteUser` / `InviteUserOptions` still say "registerInvitedUser writes it to profiles", "reads it back via get_pending_invitation and stamps it onto profiles.username", and "will read this back ... and write profiles.brand_id from it". After this spec the client writes nothing to `profiles`; `register_invited_profile()` derives role/brand/username server-side. These comments describe the trust model this spec just changed, so the next reader (or security reviewer) will be misled about who is the authority. The backend-developer deliberately left them alone to keep the diff small. They sit in `inviteUser`, not in the spec 163 region (`fetchAllUsers`, ~596-690), so fixing them does not collide with the 163 hunks. Suggested fix: reword to "the invitation row is the authority; `register_invited_profile()` (spec 164) copies role/brand/username/stores onto the profile server-side". Comment-only change.
- `supabase/tests/order_approvals.test.sql:416,418` — The `\b` -> `\y` change makes this inline OR-tail probe live for the first time, but its regex is a weaker copy of the lint's: it lacks the `(?!\s+and\y)` guard and the trailing `\s*($|\s+or\y)` anchor that `permissive_policy_lint.test.sql` uses. Now that `\y` works, a future legitimate AND-guarded shape like `... or (auth.uid() is not null and <x>)` on `order_approvals` would be a false positive here, even though the lint (arm 4) is built to pass it. The arm passes today only because no such policy exists. Suggested fix: either copy the lint's full OR-tail regex into both lines, or drop the OR-tail halves here since the global lint already covers `public.order_approvals`.
- `supabase/tests/invitations_super_admin_rls.test.sql:139` — Arm (iii) still inserts `role = 'manager'`. After spec 164 the `invitations` policy also rejects `'manager'` via the role whitelist, so this arm now gets `42501` whether or not `auth_is_privileged()` works, and it no longer isolates the privilege check it is named for. The spec said to leave (iii) unchanged, but the reason (it still returns 42501) is exactly what makes it a weak test. Suggested fix: change the literal to `'user'` so the only possible cause of the 42501 is the caller's privilege. This is a one-token change in the same file already edited for arms (i)/(ii).

### Nits
- `supabase/migrations/20261007000000_profiles_insert_hardening.sql:275-321` — The P_INV predicate is pasted three times verbatim (INSERT `with check`, UPDATE `using`, UPDATE `with check`). If one copy drifts, the policies silently diverge. Consider a `SECURITY INVOKER` helper such as `public.invitation_write_allowed(role text, brand_id uuid, store_ids text[])` called from all three. Not blocking; the design called for an inline predicate and pgTAP section D pins the behavior.
- `supabase/migrations/20261007000000_profiles_insert_hardening.sql:165-188` — The pending-invitation predicate (`lower(i.email) = v_email and i.used = false and (...)`) is written twice, once for `count(*)` and once for the `FOR UPDATE` select. A single `select ... where PEND order by ... limit 2 for update` plus a row-count check would remove the duplication, but the current form follows the design's algorithm and is correct. Only worth doing if the predicate changes again.
- `supabase/tests/permissive_policy_lint.test.sql:44-57` (header) — The documented "Detection regex" for the OR-tail omits the `(?!\s+and\y)` lookahead and the trailing `\s*($|\s+or\y)` anchor that the real regexes use. Also `:95-107` still says the detection CTE is repeated "in arms (1)+(2) and arm (3)"; it is now five copies (arms 1-5). The five 4-regex copies are the drift surface that let the original `\b` bug survive, so a one-line note pointing future editors to change all five would help (a shared view is out of scope for this spec).

- `src/lib/registerInvitedUser.test.ts:67-70` — The `from` mock still carries `insert` and `delete` builders although `registerInvitedUser` no longer touches `from` at all; the only use of `fromMock` is asserting it is not called with `profiles`/`user_stores`.
