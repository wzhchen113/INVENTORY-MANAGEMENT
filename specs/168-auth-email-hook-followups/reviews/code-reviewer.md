### Should-fix
- `scripts/smoke-send-email-hook.sh:561-570` — The S10 precondition can pass for the wrong reason. `EDGE_FROM` is read with `docker exec … printenv … 2>/dev/null` and never checked. If it comes back empty (container renamed, env unset), the probe posts `From:{Email:""}`. Mailpit then answers 400 because of the **From**, not the To, and the arm prints `PASS precondition: Mailpit … rejects 'not-an-address'`. The arm's whole premise is that this specific To is rejected. The later `status == MP_CODE` log assertion would not catch it by accident either (the hook would fail earlier with `reason:config`, so S10 would fail, but with a misleading message). Fix: `[[ -n "$EDGE_FROM" ]] || fail …` before the probe, and/or capture the response body and require it to mention the To address (`jq -r '.Error'` contains `not-an-address`). Both are a few lines.

### Nits
- `scripts/smoke-send-email-hook.sh:564` and `:571` — `mp_clear` runs twice in a row on the success path (once right after the probe, once at the start of the `else` branch). Drop the first or the second.
- `scripts/smoke-send-email-hook.sh:572` — S10 prints `PASS Mailpit cleared`, the same text as the Setup arm (`:274`). In a long run the two are indistinguishable. Something like `Mailpit cleared before S10` is clearer.
- `scripts/smoke-send-email-hook.sh:581` — the poll loop variable `i` is a top-level global (the other loops in the script use `local i` inside helpers). Harmless today, but nothing else in the script reuses `i` at top level, so a one-line comment on the poll or a `local`-style helper (`poll_s10_log`) would keep the arm body shorter. The arm body is now ~50 lines in a single `else`.
- `supabase/functions/auth-email-hook/index.ts:603-604` — "as before spec 168" in the `deliver()` comment describes history, not why. State the invariant instead: "a throw here is an internal error (500 `internal error`), not a transport failure, so it must not be classified."
- `supabase/functions/auth-email-hook/index.ts:617` — `e instanceof DOMException ? e.name : ""` uses `""` as a sentinel meaning "not a DOMException". It is correct and the design pins it, but a one-line why-comment would help ("a plain Error that happens to be named TimeoutError must stay `transport`"). Otherwise the next reader will "simplify" it to `(e as Error).name`.
- `src/lib/authEmailHook.ts:312` — `renderBody(action, newEmail, link, code)` takes four positional strings, two of which (`link`, `code`) are the same type and trivially swappable. It already has a `LinkAndCode` type; passing it would remove the hazard. The architect fixed this signature, so this is a preference, not a deviation.
- `src/lib/authEmailHook.ts:303-308` — `linkOnly` is defined once, which satisfies the "one place" criterion, but it is still consumed by two ternaries (`:304` and `:308`). That is acceptable. If you want a stricter reading of "not split across two branches", fold the hash-empty case into one expression; I would not.
- `src/lib/authEmailHook.ts:357` — `renderMail` is now the only function in the new group without a comment saying what `null` means. A one-liner ("null = unlinkable, see resolveLinkAndCode") would match its neighbours.
- `src/lib/authEmailHook.golden.test.ts:106` and `:131` — `A.recovery` and `C.recovery_redirect_no_query` are identical inputs, so the second adds no coverage. Harmless, and the names track the spec's group lettering. Fine to leave, or note it in a comment.
- `src/lib/authEmailHook.golden.test.ts:208-258` — a module-level `if (CAPTURE) { describe(…) } else { describe(…) }` where the capture "test" always throws is unusual. It is explained in the file header and is the right trade for the guard design (a capture run is never green). No change requested. Consider moving `canonicalBlockSha256`'s duplicate of the parity test's extraction rule behind a comment pointing at the parity test (the header says "same extraction rule", which is already enough).
- `src/lib/authEmailHook.test.ts:510` — the `data()` helper builds `email_data` from `payload('magiclink', …)` and the tests then pass a different `action` string to `resolveLinkAndCode`. It works because the function takes `action` as its own argument and ignores `d.email_action_type`, but it reads as a mismatch. Optional: override `email_action_type` in the helper.
- `src/lib/authEmailHook.test.ts:553-563` — the `renderBody` test packs two behaviours (notification has no ignore line; empty link has no anchor) plus a third (code rendered) into one `it`. Splitting into three `it`s would give better failure messages.
- `scripts/probe-auth-email-hook.sh:80` — `unset SECRET HOOK_SECRET`: `HOOK_SECRET` was already unset at `:65`, so it is now a no-op. The spec said the line stays, so keep it; just be aware it is belt-and-braces, not load-bearing.
- `scripts/probe-auth-email-hook.sh:60-62` — the comment "Checked before the secret is read…" sits directly under the placeholder-`--to` check, so it reads as if it describes that check rather than the `command -v node` line below it. Add a blank line above the comment or move the comment to sit immediately above line 62.
