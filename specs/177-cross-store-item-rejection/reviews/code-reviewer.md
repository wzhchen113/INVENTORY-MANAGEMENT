### Should-fix
- `supabase/tests/cross_store_item_rejection.test.sql:263-268` (T16), `:474-479` (T34), `:612-617` (T48) — These three arms are described as pinning the in-function short-circuit (design D-4 / N1: "a pass-through SET is accepted (short-circuit)"). They do not pin it. In T16 and T34 the row is same-store, so the full check would also pass without the short-circuit. In T48 the lock function compares `new` to `old` regardless, so it has no short-circuit to pin. Delete the short-circuit from `po_items_check_store()` or `order_approvals_lines_check_store()` and these arms stay green, so the D-4 claim is unproven. The test header's "every acceptance arm re-reads the row (anti-vacuity)" (L13) also overclaims for these three. Fix: for T16 and T34, make the existing row cross-store first (as postgres, `update inventory_items set store_id = <other> where id = <item>`; this is the out-of-scope residual vector, which makes it a faithful model), then run the pass-through as master or admin and assert it succeeds. Alternatively, soften the descriptions and the design claim to "pass-through is accepted" and drop the short-circuit wording. T48 should only drop the "short-circuit" wording. Coverage is the test-engineer's lane; I raise it here because the descriptions assert something the SQL does not prove.

### Nits
- `supabase/migrations/20261025000000_cross_store_item_rejection.sql:40-45` (and `:143-149`) — `pg_input_is_valid` is a PG16+ function and this is its first use in the repo. plpgsql binds late, so on PG < 16 the migration would apply cleanly and every `order_approvals` write would then fail at fire time. Prod and local are PG17 (`config.toml:36`) and the spec §10 runbook checks `version()`. Still, the PROD-APPLY header an operator actually reads does not say it. Add "requires PG >= 16 (pg_input_is_valid)" to the header.
- `supabase/migrations/20261025000000_cross_store_item_rejection.sql:84-87` — A null `item_id` raises the "item store mismatch" message. This is stable and pinned by T11 and the design, but the message is slightly misleading for a missing item. If the messages are ever revisited, a distinct string would read better. No action needed now.
- `supabase/migrations/20261025000000_cross_store_item_rejection.sql:92` — `v_item_store is null or v_item_store is distinct from v_po_store`. `v_po_store` is already proven non-null at this point, so `<>` would be enough. It mirrors the precedent, so leave it.
- `supabase/tests/cross_store_item_rejection.test.sql:394-431` (T28, T29) — These call `create_order_approval` in `do $$ … perform … $$` blocks instead of `lives_ok`. If the RPC ever regresses, the file aborts mid-transaction and the TAP plan is lost, rather than reporting one failed arm. Use `lives_ok` and store `d5_id` / `d5_lines` in a separate statement.
- `supabase/tests/cross_store_item_rejection.test.sql:107-114` — `pg_temp.l177` is declared `immutable`, but `jsonb_build_object` is `stable`. It is harmless in a temp function, but `stable` is correct.
- `supabase/tests/cross_store_item_rejection.test.sql:310` — T02 sits after T20 in file order, so numbering is non-monotonic. The header's "T01–T54" reads fine, but this is a small trap for the next reader.
- `supabase/tests/cross_store_item_rejection.test.sql:628-656` (T49-T51) — Three copy-pasted probes. A single `select ok(...)` over `unnest(array['po_items_check_store', …])` would keep the plan at 54 and remove the repetition. Preference only.
- `supabase/tests/report_last_order_context.test.sql:354-407` — The disable/enable wrapper covers all eleven fixture rows, not only the malformed G1/G2 row, so the ten well-formed rows skip trigger validation too. That is exactly what AC-16 permits ("wrapping the existing INSERT"), and the comment says "this one fixture INSERT only", which is accurate. Not a finding against the implementation; noted so nobody "tightens" it later by splitting the INSERT, which AC-16 forbids.
